# S2 契约篇 · 流式事件协议

> **阶段**：S2（pi-ai 流式事件协议）。
> **用途**：复习时只看这里；字段细节查源码。
> **实现**：`src/PiUnityAgent.Ai/Events/`。
> **配套**：`S2-流式事件协议-概念篇.md`、`Q&A.md` Q12–Q17。

---

## 强制级别总表

| 契约 | 强制级别 | 谁来保证 |
|---|---|---|
| 顺序与生命周期 | **约定 + 测试**，无运行时校验 | provider 生产者 |
| 终态分类 | **运行时硬校验** | `AssistantMessageEventValidation` |
| partial 快照 | 类型 + 约定 | 事件形状 |
| contentIndex 归属 | 约定 + 测试 | provider 生产者 |
| 单消费者 | Channel 提示 + 约定，无守卫 | 调用方 |
| 计时 | 运行时 | `AssistantMessageEventStream.Time` |
| 取消双通道 | 运行时（消费侧）+ provider（生产侧） | 两侧各自 |
| 错误 vs 异常 | 运行时 | `EventStream.Fail` |
| 收场后行为 | 运行时 | `_ended` 守卫 |

---

## 卡 1 · 顺序与生命周期

- **必须成立**：`start` 先于所有更新和终态；每个块的 `start → delta* → end` 自成序列，delta 不能跨块；终态恰好一个且最后。
- **例外**：请求建立阶段就失败时，可以直接以 `error` 结束，**没有 `start`**。
- **在哪强制**：S2 不做顺序校验，靠 provider 实现 + 事件序列测试。
- **破坏后果**：UI 把 delta 应用到不存在的块；agent loop 状态机错位。
- **验收问法**：如果 provider 先推 `text_delta` 再推 `start`，谁会拦住？

> 答案：没人拦。这是**生产者责任**，S2 只提供容器，不替 provider 做状态机。

---

## 卡 2 · 终态分类与唯一性

- **必须成立**：
  - `Done` 只能是 `Stop / Length / ToolUse / Deferred`；
  - `Error` 只能是 `Error / Aborted`；
  - 一个流恰好一个终态；
  - 终态之后不再有事件。
- **在哪强制**：`AssistantMessageEventValidation.Validate`，在 `AssistantMessageEventStream.Push` 里调用（运行时硬校验）。
- **破坏后果**：下游把截断当失败、把取消当错误；`WaitForDone` 拿到不一致的结果。
- **验收问法**：为什么 `Length` 属于 `Done`，而 `Aborted` 属于 `Error`？

> 答案：`Length` 是"正常结束但被截断"，不是环境故障；`Aborted` 是"被叫停"，与 `Error` 同属非正常收场，但语义不同、重试策略不同。

**补充**：非法终态 reason 会**同步抛给生产者**（fail-fast），这是有意的——bug 应该当场暴露，而不是被包装成错误事件。

---

## 卡 3 · partial 快照与权威性

- **必须成立**：
  - 每个事件携带"当前累计消息"的快照；
  - `Partial` 属性指向最新快照；
  - `start` 之前为 `null`，终态后为 final；
  - 下游**不得原地修改**快照，也不得依赖对象同一性。
- **权威性**：`*_end` 与 final 才是权威；delta/partial 可能不完整——
  - 工具参数 delta 是 JSON 片段；
  - 脱敏思考可能 start 时已完整、没有任何 delta；
  - 文本 end 带完整文本，delta 不保证齐全。
- **在哪强制**：不可变 record + `volatile Partial`；其余靠约定。
- **破坏后果**：下游拼出错误内容；把脱敏思考当空块丢掉签名。
- **验收问法**：第 N 个 `text_delta` 的 `Partial` 文本，一定等于最终文本的前缀吗？

> 答案：**不保证**。它只是"到目前为止的最好快照"；协议保证的是 end/final。

---

## 卡 4 · contentIndex 归属

- **必须成立**：`ContentIndex` 是**最终 `Content` 数组中的位置**，不是"第几个块事件"；同一个块从 start 到 end 索引不变；一条回复可有多个块并存。
- **在哪强制**：事件字段 + 生产者实现；测试覆盖多块场景。
- **破坏后果**：文本和工具调用串位；UI 把工具参数显示到文本块里。
- **验收问法**：回复是 `[思考, 文本, 工具调用]`，文本 delta 的 index 是 1 还是 0？

> 答案：**1**——最终内容里的位置。这是最容易写错的一条。

---

## 卡 5 · 单消费者与缓冲

- **必须成立**：
  - 一个流只有一个消费者；
  - 不承诺广播；
  - 消费者未开始前，事件按 FIFO 缓冲；
  - unbounded，不做背压。
- **在哪强制**：Channel 的 `SingleReader = true` 只是**性能提示，不是守卫**——开两个迭代器不会报错，而是**事件被抢走、各读一半**。
- **破坏后果**：UI 和 agent loop 各拿一半事件；事件静默丢失。
- **验收问法**：我想同时给 UI 和日志看事件，应该在哪一层做？

> 答案：在 agent 层转发（一个消费者读，再分发给多个观察者），**不要开两个迭代器**。

---

## 卡 6 · 计时

- **必须成立**：
  - 流创建时开始单调计时；
  - 终态消息（或 `End` 入参）写入 `DurationMs`；
  - 若消息已有 `DurationMs`，不覆盖；
  - 若消息 `Timestamp` 早于流创建时刻，不覆盖（响应在别处开始）；
  - 结果限制在 `int` 范围。
- **在哪强制**：`AssistantMessageEventStream.Time`，运行时。
- **破坏后果**：deferred/转发响应被误计时；下游自己计时与底座不一致。
- **验收问法**：为什么"时间戳早于流创建"就不写 duration？

> 答案：说明这条响应是别处开始、这里只是转发（例如 deferred fetch），计时应归原流。

---

## 卡 7 · 取消的两条通道

- **必须区分**：
  - **消费者取消**：`GetAsyncEnumerator(ct)` / `WaitForDoneAsync(ct)` → 抛 `OperationCanceledException`，不挂死；**不会自动停生产者**。
  - **生产者取消**：v2 起只有 `SimpleStreamOptions.CancellationToken` → provider 内层流产生 `Error(Aborted)` 终态，保留 partial；LazyStream setup 异常（含 OCE）统一 `Error(Error)`。
- **在哪强制**：消费侧在 `EventStream`（`WaitToReadAsync(ct)`、`WhenAny` + 注册）；生产侧在 provider。
- **破坏后果**：
  - 消费侧：UI 卡死；
  - 生产侧：取消后仍推事件，或把取消写成 `Error` 触发重试。
- **验收问法**：用户点了停止，但只取消了迭代器 token，provider 会停吗？

> 答案：**不会**。必须用生产侧 token 才能真正中止请求。

---

## 卡 8 · 错误 vs 异常（`Fail` 语义）

- **必须成立**：
  - 模型/网络/取消 → **终态事件**；
  - `Fail(exception)` 只用于**基础设施故障**；
  - `Fail` 后，已入队事件可先被消费，然后**原样抛原始异常**（不是 `ChannelClosedException`）；
  - `WaitForDoneAsync` 同样抛原始异常；
  - `Push` 的完成判定/结果提取回调抛异常 → 流以该异常失败。
- **在哪强制**：`EventStream.Fail` / `Push` 的 try-catch；测试覆盖。
- **破坏后果**：模型错误以异常穿透 agent loop；异常被包装后丢掉原始类型/堆栈；调用方误判为基础设施故障。
- **验收问法**：provider 返回 500，应该 `Push Error` 还是 `Fail`？

> 答案：**`Push Error`**。500 是模型/服务失败，属于业务路径；`Fail` 留给"流本身坏了"。

---

## 卡 9 · 收场后行为

- **必须成立**：
  - 终态后 `Push` 被忽略；
  - 终态后 `End` / `Fail` 是 no-op；
  - `WaitForDoneAsync` 始终返回那个终态消息；
  - 迭代器把已入队事件发完后正常结束。
- **在哪强制**：`EventStream._ended` + `AssistantMessageEventStream` 入口守卫，运行时。
- **破坏后果**：重复终态、结果被覆盖、状态机抖动。
- **验收问法**：终态后又推一个 delta，消费者会看到吗？

> 答案：**不会**。事件被静默丢弃。

## S2 相对 pi / pi.net 的契约偏离

| 项 | pi / pi.net | 我们 | 原因 |
|---|---|---|---|
| partial | pi 活对象；pi.net 快照 | 快照 | record 生态 + 线程安全 + 可记录 |
| 事件扩展字段 | pi.net 有 `Sequence`/`Index`/`Signature` | 无 | 对齐 pi 原版，保持最小 |
| `Fail` 异常 | — | 原样抛，不包 `ChannelClosedException` | 与 Channels 实际行为一致，已实测 |
| 并发 Push | — | **单生产者**；check-then-act 非原子 | 已知限制，写入 XML 注释 |
| 广播 | 不支持 | 不支持 | 明确单消费者 |
| 事件持久化 | 不持久化 | 不持久化 | S10 只存 final 消息 |

## 验收问题

1. 为什么非法终态 reason 要同步抛给生产者，而不是转成错误事件？
2. `Length` 为什么是 `Done` 而不是 `Error`？
3. 第 N 个 delta 的 partial 为什么不能当作最终文本的前缀来信任？
4. 两个迭代器同时消费同一个流会发生什么？应该怎么替代？
5. 消费者取消和生产者取消分别影响什么？为什么不能混为一谈？
6. provider 返回 500，走 `Push Error` 还是 `Fail`？为什么？
