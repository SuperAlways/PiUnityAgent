# 03 · 开发方法：拆解、学习与移植约定（2026-11-04）

> **状态**：方法约定 v1.4（2026-11-07，新增 §1.5 后置能力交接治理）。
> **用途**：规定本项目的开发节奏、参考源顺序、讲解交付物与移植纪律。
> **适用**：所有参与本项目的实现者（人或 AI）。
> **一句话**：**以最新原版 pi 为行为真相源，先拆解再重做；Pi.NET 只作 C# 语言映射参考；每个开发循环都必须产出"能讲清的心智模型 + 可运行代码 + 可调优说明书"。**

---

## 一、目标与角色

### 1.1 两层目标

| 目标 | 内容 |
|---|---|
| **学习（更根本）** | 拆解工业界最强的 agent 项目（pi），重做成 C#；通过"拆解→讲解→实现→对照"建立坚实心智模型，能决策、能调优 |
| **产品（自然结果）** | 一个 netstandard2.1 的 C# agent 底座（pi-ai + pi-agent-core **全量严格照搬**），个人可用，并开源给 C# 游戏 mod 开发者与游戏厂商 |

### 1.2 三个参考角色

| 角色 | 是谁 | 怎么用 | 优先级 |
|---|---|---|---|
| **行为真相源** | 最新原版 pi（TypeScript） | 语义、协议、循环、事件顺序、失败模式、可调参数 | **第一** |
| **C# 语言映射参考** | Pi.NET（net9/net10，本地 `pi-study/pi.net`） | 只看 TS 与 C# 特性不同时它怎么处理 | **第二** |
| **产物** | 本项目的 netstandard2.1 重构 | 语义等价 + C# 惯用法 + Unity 可用 | — |

> **"先看两边"的固定顺序：先读最新原版 pi，再看 Pi.NET。** 反过来的风险是：把 Pi.NET 的实现当作行为标准，而它本身可能偏离上游、或有 port 缺陷。

### 1.3 阶段一对齐总则（强制，2026-11-06）

**适用范围**：第一阶段 = `pi-ai` + `pi-agent-core`（不是 pi-coding-agent 的 CLI/TUI/编码工具集）。S1–S8 的所有模块必须遵守。

**判定顺序（不可颠倒）**：

1. **行为与形状以 pi 原版为准**：类型、字段、默认值、事件顺序、失败模式、可调参数。
2. **语言 / 生态差异 → 借鉴 pi.net**：同一个 TS 特性在 C# 里怎么写；只换表达，不换语义。
3. **Unity / netstandard2.1 独有约束 → 做取舍**：只有这类约束可以偏离；必须写明替代方案与代价。

**四条硬规则**：

- **形状不可裁剪**：公共类型、接口、字段、可选成员必须存在；行为可以后置（`TODO` / `NotSupportedException` / 错误结果），但**不能没有这个成员**。"用不到"不是删除公共 API 的理由。
- **偏离必须登记**：每个 spec/plan 必须附三方偏离表：`pi 原版 | pi.net | 我们 | 原因 | 代价 | 是否可避免`。只写"范围边界"而不写"形状缺失"= 违规。
- **偏离分级**：A 语言/生态强制；B 借鉴 pi.net 的 C# 映射；C 行为后置（形状必须保留）；D 我们主动加固（必须说明收益与代价）。
- **下游零适配优先**：S4–S13 引用 S1–S3 时不应为补齐形状而返工；若必须返工，说明形状对齐没做够。

**spec 通过前的五个自查**：

1. 这个能力在 pi 原版的公共形状里存在吗？我们的形状有对应成员吗？
2. 如果没实现，是"行为后置"还是"形状缺失"？后者必须补。
3. C# 差异是语言强制，还是偷懒？偷懒的必须改回 pi 语义，或登记为 C/D。
4. pi.net 在同一生态里解决了吗？怎么解决的？它是否偏离了 pi？
5. Unity/2.1 约束是真的硬约束吗？替代方案与代价写了吗？

**反例（S3 复盘，2026-11-06）**：把 `Provider` 缩成 record + 单个 `StreamFn`，`Models` 只留 6 个方法，`Model` / `SimpleStreamOptions` 缺 `Compat` / `SamplingParams` / `Fetch` / `OnResponse` 等字段——这是"形状缺失"，不是"行为后置"，必须返工对齐。

### 1.4 跨组件契约（通讯层，强制，2026-11-07）

第一阶段采用 **B 方案**：**PiUnityAgent 自己拥有通讯端口**，`UnityLlmTransport` 是实现/适配方，不是 `Ai` 的依赖。

- **端口在 Ai**：`FetchFunction` / `FetchRequest` / `FetchOptions` / `IFetchResponse` / `FetchException` / `TransportKind` 定义在 `PiUnityAgent.Ai`；形状对齐 pi 的 `fetch?: FetchFunction`。
- **Ai 不引用通讯组件**：`Ai` 不得引用 `UnityLlmTransport` / `UnityEngine` / 任何具体传输；具体实现由 Host 注入。
- **适配器在 Host**：`PiUnityAgent.Hosts.Unity` / `Ext` 负责 `Fetch 端口 ↔ IStreamingHttpTransport` 映射；适配器可引用 Unity 与通讯组件。
- **事实源分工**：通讯事实（流式/取消/超时/版本矩阵）以 `UnityLlmTransport/docs/` 为准；协议事实以 `PiUnityAgent/docs/` 为准；接缝以 `docs/07-通讯层集成契约.md` 为准。
- **版本锁**：每个引用通讯组件的 spec/plan 必须写 commit/tag；当前锁 `UnityLlmTransport@87db637`（Phase 2 终审，2026-11-07）。
- **不得重复形状**：`Ai` 不得再定义与端口重复的传输类型（例如第二份 `IStreamingHttpTransport` 或 `TransportOptions`）；`Transport` 统一叫 `TransportKind`。
- **SSE/协议语义在 Ai**：传输层只吐字节；`[DONE]`、`data:`、`tool_calls`/`usage`/`stopReason` 全部在 `Ai`。

### 1.5 后置能力交接治理（强制，2026-11-07）

“形状先补、行为后置”不是一次性标注，必须走可执行台账与阶段门禁。权威规则见 [`docs/SOP/后置能力交接治理-SOP-2026-11-07.md`](SOP/后置能力交接治理-SOP-2026-11-07.md)。

- **唯一台账**：`docs/待办-后置能力.md`；每条 Dn 必须有形状锚点、验收测试锚点、目标阶段、状态。
- **代码锚点**：`TODO(Sx, Dn)` / `NotSupportedException("Deferred to Sx: ... (Dn)")`；禁止无 Dn 的“以后再做”注释。
- **阶段开工**：每个阶段 plan 的第一个任务必须是“承接后置能力”，把目标阶段为当前阶段的 Dn 转成行为测试；未纳入必须用户批准重排期。
- **阶段收尾**：`python scripts/check-deferred.py --root . --current-stage <Sx> --gate exit` 必须通过；目标 Dn 未完成或已完成仍残留 stub → 阶段不得完成。
- **完成定义**：删除 stub、验收测试转绿、台账填完成提交、状态改 `已完成`；三者缺一不可。

## 二、参考源纪律（强制）

1. **先原版，后 Pi.NET。** 每个模块动工前，先读原版 pi 的源码/文档，弄清"它做什么、为什么、边界在哪"；然后再看 Pi.NET "用 C# 怎么表达"。
2. **版本打钉。** 每个模块开工前记录：
   - 原版 pi：tag + commit（本地参考已同步 v1.5.0 / f9a263655 / 2026-11-02；**开发当日仍应先确认最新 tag**）；
   - Pi.NET：版本 + 对应上游 commit（当前 `main 2d6757b`；最新 tag `v1.4.5` + 40 commits；docs 对齐上游 v1.5.0）。
   - 记录位置：模块讲解卡 + 决策日志。
3. **冲突时以原版 pi 为准。** Pi.NET 与 pi 行为不一致时，按 pi 实现，并在决策日志登记差异。
4. **不直接抄 Pi.NET 的业务逻辑。** 它只回答"这个 TS 特性在 C# 里怎么写"；协议、状态机、事件顺序、错误契约仍以 pi 为准。
5. **不盲目追最新。** 原版 pi 迭代快；每个批次只对齐一个明确 tag，发现上游漂移先记录，不随手跟。

### 2.5 参考源同步与版本打钉（每个模块/批次开工前）

**频率**：每个模块或批次开始时同步一次；模块进行中不换版本。

**原版 pi**：

```bash
git -C pi-study/pi fetch --tags --prune
git -C pi-study/pi tag --sort=-v:refname | head -5
git -C pi-study/pi log -1 --date=short --format="%h %ad %s"
```

- 若本地不是最新 tag：检出最新 tag，或明确固定某个 tag（二选一，写进版本卡）。
- 记录：tag / commit / 日期。

**Pi.NET**：

```bash
git -C pi-study/pi.net fetch --tags --prune
git -C pi-study/pi.net describe --tags --abbrev=0
git -C pi-study/pi.net log -1 --date=short --format="%h %ad %s"
```

- 读 `docs/migration-execution-status.md` 的当前口径（对齐到哪个上游版本、哪些包未完成）。
- 记录：版本 / commit / 日期。

**网络**：参考仓库不继承本仓库代理时，单独配置或命令内指定：

```bash
git -c http.proxy=http://127.0.0.1:7897 -C pi-study/pi fetch --tags
```

**版本卡**：写入讲解卡 §0 与 `PORTING.md`；同时记录"上游领先/落后本模块多少"。同步结果不确定时，宁可固定旧 tag，也不要边写边换。

## 三、每个模块的开发循环

```
选模块/定边界
  → 同步参考源并打钉（§2.5）
  → 读 pi（原版）
  → 阶段 0：宏观概念讲解（无代码，图 + 概念）→ 你提问 → 概念篇
  → 阶段 1：pi 源码导读（有代码，模块/文件/函数）→ 你提问 → 源码篇
  → 阶段 2：实现设计（pi 原版 → pi.net → Unity/2.1 → 鲁棒性/性能 → 下游零适配 → 最小偏离）→ spec（用户 review）
  → 阶段 3：plan（writing-plans）→ subagent + Haiku → 强模型审查 → 对照/门禁
  → 阶段末：教学篇 + 学习问答记录 + 心智模型/调优手册
  → 门禁
```

### 3.0 三方对照（贯穿）

| 顺序 | 看谁 | 回答什么 |
|---|---|---|
| 1 | **原版 pi** | 行为、不变量、事件顺序、失败模式、可调参数 |
| 2 | **Pi.NET** | 同一个 TS 特性在 C# 里怎么写、它踩过什么坑 |
| 3 | **我们的 2.1 实现** | 语义等价、Unity 可用、单测通过 |

- **冲突以原版 pi 为准**；Pi.NET 的偏离登记在讲解卡 §8。
- 我们的偏离（裁剪、拆分、命名、2.1 妥协）登记在 `PORTING.md` 与决策日志。
- 不要求逐字节一致，要求消息序列、工具调用、事件顺序、终止条件语义一致。

### 3.1 选模块

- 一次只做一个可独立讲清的模块（例如"流式事件协议""工具执行""压缩"）。
- 模块边界写进讲解卡；跨模块依赖先列出来，不边做边扩。

### 3.2 读原版 pi

必须回答这六个问题，写进讲解卡：

1. 输入是什么、输出是什么？
2. 状态机/数据流怎么走？
3. 三条关键不变量是什么？
4. 失败模式有哪些（网络、超时、中止、错误参数、空结果）？
5. 事件顺序是什么（谁先谁后，哪些是屏障）？
6. 有哪些可调参数（阈值、并发、预算、超时）？

### 3.3 教学型 brainstorming（先讲再做，第一阶段必做）

**目标**：先建立宏观心智模型，再看源码，最后才做实现设计。不是问用户想做什么，也不是一上来给方案。

**下游**：后续 S2–S13 中大量引用/调用 `PiUnityAgent.Ai` / `Core` 的代码。底座形状一旦偏离，下游就要写适配层——这是最想避免的成本。

#### 阶段 0 · 宏观概念讲解（无代码）

- 这块是干什么的；
- 在整个 agent 系统中起什么作用；
- 关键概念、术语、数据流；
- 用图和易懂的方式讲，**不涉及代码**；
- 讲完后由用户展开提问，我回答、补充、纠正；
- 产出：**教学讲解文档（概念篇）**。

#### 阶段 1 · pi 源码导读（有代码）

- 用图讲模块、文件、函数；
- 每个模块/文件/函数在系统中的职责；
- 调用链、数据流、事件顺序；
- 和概念篇一一对应、互相巩固；
- 讲完后用户继续提问，我回答；
- 产出：**源码导读文档（代码篇）**。

#### 阶段 2 · 实现设计（spec）

- 对照 **pi（原版）**；
- 对照 **pi.net** 的 C# 转化；
- 考虑 **Unity / netstandard2.1** 的语言与生态限制；
- 考虑**鲁棒性、性能**；
- 保证**下游零适配 / 贴合**；
- 给出**最小偏离**推荐与代价；
- 产出：**spec**，由用户 review。

#### 阶段 3 · plan → 实现 → 教学沉淀

- spec 通过后写 **plan**；
- 用 **subagent + Haiku** 搬运/生成代码；
- 强模型审查、对照、门禁；
- 阶段末：**教学篇 + 学习问答记录**。

#### 实现设计阶段的处理顺序（强制）

1. 先看 **pi（原版）** 的定义：语义、字段、默认值、事件顺序。
2. 再看 **pi.net** 的 C# 实现：类型形状、写法、取舍，以及它是否偏离 pi（原版）。
3. 再看 **Unity / netstandard2.1** 的硬约束：API 缺失、序列化、AOT/IL2CPP、主线程、程序集加载。
4. 给出**保持性能与鲁棒性下最小偏离**的推荐：
   - 默认贴 pi（原版）语义 + pi.net 形状；
   - **不得以"用不到"为由裁剪公共类型/接口/字段**；行为可后置，形状不可缺（§1.3）；
   - 只有 Unity/netstandard2.1 硬约束才偏离；
   - 偏离必须说明代价（性能、AOT、兼容性、下游适配成本）。
5. **最后才反问用户**，确认心智模型/选择。

> 判断标准：**下游零适配 > 形状贴 pi（原版）/pi.net > 局部性能/鲁棒性不下降 > 发明新设计**。
> 阶段 0/1 是用户主导提问；阶段 2 是我先做功课、先给推荐，再问用户。

**必须覆盖的差距清单**：

- 语言：union→record、AbortSignal→CancellationToken、AsyncIterable→IAsyncEnumerable、typebox→JSON Schema、可选/空值语义；
- 生态：Node/Bun vs Unity Mono/netstandard2.1、SSE（fetch/undici vs UnityWebRequest/HttpClient）、文件/HTTP、程序集加载（jiti/ALC）、IL2CPP/AOT、主线程。

**pi.net 对照**：对每个差距，指出 pi.net 的文件/写法/取舍，以及它是否偏离 pi（原版）。

**三方偏离表（spec 必附）**：每个差距一行，列出 `pi 原版 | pi.net | 我们 | 偏离类别（A/B/C/D）| 原因 | 代价 | 是否可避免`。没有这张表的 spec 不进入 plan。

**输出**：brainstorming 笔记（概念图、模块/文件/函数图、差距表、pi（原版）/pi.net 写法、最小偏离清单与理由、用户问答、心智模型缺口）→ spec 输入。**阶段 0/1 结束前不改代码、不写 spec/plan。**

### 3.4 查 pi.net

- 只查"语言映射"：union→record、AbortSignal→CancellationToken、AsyncIterable→IAsyncEnumerable、typebox→JSON Schema、`Lock`/`Task.WhenEach` 等 net9 特性的替代。
- 记录 pi.net 的取舍与坑（例如它依赖 net9 API、全量 provider 带来的复杂度）。

### 3.5 spec / plan / TDD

- 遵循项目既有 superpowers 流程：spec → plan → TDD。
- **Faux provider 先行**：先让循环在无网络、无密钥下可测，再接真实 provider。
- Core 必须有单测；宿主适配靠契约 + 实机。

### 3.6 对照验证

- 用同一组场景，在以下三者上跑并对比事件流：
  1. 原版 pi（TS，行为基准）；
  2. Pi.NET（C# 参考）；
  3. 我们的实现。
- 对比维度：消息序列、工具调用顺序、事件顺序、终止条件、错误编码。**语义一致即可，不要求逐字节一致。**
- 对照结果写入模块讲解卡的"差异"一节。

### 3.7 复盘

- 每个批次结束做一次复盘：哪里理解错了、哪里 C# 表达别扭、哪些参数需要调。
- 复盘产出：更新心智模型文档 + 调优手册 + 决策日志。

### 3.8 门禁（模块完成定义）

一个模块算完成，必须同时具备：

- [ ] 代码可运行、Core 单测全绿；
- [ ] 参考源同步记录（版本卡，§2.5）；
- [ ] 讲解卡（§四模板）；
- [ ] 教学文档（`docs/learning/` 对应篇章，§五）；
- [ ] 对照记录（与原版 pi / Pi.NET 的差异）；
- [ ] 决策日志（如有取舍）；
- [ ] 调优手册条目（如有旋钮）；
- [ ] 无 net9/net10 专有 API（netstandard2.1 可编）。

## 五、教学文档体系（持续更新，留在仓库里）

**对话流是主教学现场**：多用图、时序、概念对比、具体代码片段讲解；你边看边问，我边答边补。**教学型 brainstorming 的问答与差距表**要先落一份笔记，再写 spec。文档是阶段末的沉淀，不是替代。分两套：

### 5.1 `docs/learning/` —— 教人

```
docs/learning/
├─ 00-导读.md                       # 怎么读这个移植、怎么用这套文档
├─ S<N>-<topic>-概念篇.md           # 阶段0：无代码宏观概念 + 用户问答
├─ S<N>-<topic>-源码篇.md           # 阶段1：pi 源码模块/文件/函数导读（有代码）
├─ S<N>-<topic>.md                  # 阶段末：实现后的教学篇（代码/测试/差异）
├─ Q&A.md                           # 用户提问 + 回答 + 纠正，持续追加
└─ 心智模型.md                       # 状态机/事件时序/上下文组装图
```

- **概念篇**：这块是什么、在 agent 系统里的位置、关键概念、数据流图、常见误解、用户问答；不写实现代码。
- **源码篇**：pi（原版）的模块/文件/函数图、调用链、与概念篇的对应、用户问答；有代码，但不等于实现。
- **教学篇**：实现后的代码地图、测试、与 pi（原版）/pi.net 的差异、调优。
- `Q&A.md` 记录用户的疑问、误解与纠正；这是后人最有价值的部分。
- 每个模块的 DoD 包含概念篇、源码篇、教学篇；**没有教学文档不算完成**。
- 文档留在仓库里，跟代码一起提交、一起演进，不放在聊天记录里。

### 5.2 `docs/model/` —— 查证

```
docs/model/
├─ 00-总览.md            # 一张图：消息→上下文→模型→工具→回写
├─ 01-agent-loop.md      # 状态机、turn 生命周期、事件顺序
├─ 02-events.md          # 流式事件协议、partial 语义
├─ 03-tools.md           # 工具契约、并发、前后钩子、错误
├─ 04-context.md         # 上下文组装、system message、工具声明
├─ 05-session-compaction.md
├─ 06-skills-extensions.md
└─ 07-providers.md       # provider 差异、认证、usage/成本
```

每篇固定结构：**一张图 + 三条不变量 + 失败模式 + 调优旋钮**。不抄书，只写"我们自己的理解"。

> 两套的分工：`learning/` 负责"为什么、怎么想、怎么练"；`model/` 负责"一页纸查证"。讲解卡（§四）是模块级入口，写完沉淀到这两套里。

## 七、调优手册（随模块积累）

至少覆盖这些旋钮：

| 旋钮 | 影响 | 典型默认 | 症状与调法 |
|---|---|---|---|
| 最大轮次 / turn 上限 | 成本、卡死风险 | 待定 | 循环不收敛 → 降上限 + 检查工具结果 |
| 工具执行模式 | 延迟、顺序、副作用 | parallel | 有写操作/顺序依赖 → sequential |
| 工具并发数 | 延迟、游戏主线程压力 | 待定 | 卡帧/主线程争用 → 降并发 |
| 压缩阈值 | 上下文成本、记忆连续性 | 待定 | 频繁超限 → 降阈值；丢失关键事实 → 升阈值 |
| thinking level | 质量、成本、延迟 | 按模型 | 简单任务降档；复杂规划升档 |
| 超时 / 重试 | 稳定性、玩家等待 | 待定 | 超时频繁 → 查网络/模型；重试过多 → 降次数 |
| token 预算 | 成本 | 待定 | 超预算 → 压缩/裁剪工具结果 |
| max tokens | 单次输出长度 | 按模型 | 截断 → 升；成本高 → 降 |
| 工具结果截断 | 上下文大小 | 待定 | 大结果撑爆上下文 → 截断 + 结构化摘要 |

## 八、移植范围与 C# 映射

### 8.1 范围

| 层 | 移植 | 不移植 |
|---|---|---|
| **pi-ai** | **全部公共类型/API/能力面**：42 家 provider、OAuth、图片、classifier、deferred、嵌套工具调用、telemetry wire 等全部保留；实现按阶段推进 | —（可以用不到，但不能没有） |
| **pi-agent-core** | 全部（约 2,519 行） | — |
| **coding-agent 机制** | 只取 Session/Compaction/Skills/Extensions/Resources | CLI/TUI、bash/文件/编辑工具、project trust、export/share、MCP/codemode/durable/env（不属于两个核心包） |

> **未实现的能力标 `TODO` / `NotSupportedException`，不删除类型、不改语义；接口、字段、可选成员等公共形状同样不得删除；任何偏离登记在 `PORTING.md`、三方偏离表与决策日志。**

### 8.2 包名与文件映射

| 上游 | 我们 |
|---|---|
| `@earendil-works/pi-ai` | `PiUnityAgent.Ai` |
| `@earendil-works/pi-agent-core` | `PiUnityAgent.Core` |
| `pi-coding-agent` 中抽取的 Session/Compaction/Skills/Extensions/Resources | `PiUnityAgent.Runtime` |
| 宿主适配 | `PiUnityAgent.Hosts.Unity` / `PiUnityAgent.Hosts.Net8` |
| 可选能力包 | `PiUnityAgent.Ext.*` |

- C# 命名空间不能含连字符；程序集/命名空间统一 PascalCase。
- NuGet 包 ID 与程序集同名：`PiUnityAgent.Ai`、`PiUnityAgent.Core`、`PiUnityAgent.Runtime`。
- 文件名尽量保留上游 stem：`agent-loop.ts` → `AgentLoop.cs`；`stream-fn.ts` → `StreamFn.cs`；`types.ts` 拆到 `Types/` 并留 `_mapping.md`。
- 逐文件映射维护在 `PORTING.md`（待建）。

### 8.3 映射

| TS | C# |
|---|---|
| discriminated union | abstract record + pattern matching |
| `AbortSignal` | `CancellationToken` |
| `AsyncIterable<T>` | `IAsyncEnumerable<T>` |
| typebox schema | 轻量 JSON Schema 模型（或 NJsonSchema） |
| `convertToLlm` / `transformContext` | `Func<...>` / 接口 |
| `AgentMessage` declaration merging | `IAgentMessage` + 自定义实现 |
| 事件对象 | sealed record |
| `StreamFn` | 委托，返回 `IAsyncEnumerable<AssistantMessageEvent>` |

### 8.4 netstandard2.1 约束

- 可用：`IAsyncEnumerable`、`Span`、`Task`、`HttpClient`（Unity 侧用 UnityWebRequest）。
- 需要包：`System.Text.Json`（或改用 Newtonsoft）、`System.Threading.Channels`。
- 需要 polyfill：`IsExternalInit`、`RequiredMemberAttribute`、`CompilerFeatureRequiredAttribute`、`SetsRequiredMembersAttribute`。
- 禁止/替换：`System.Threading.Lock`、`Task.WhenEach`、`Base64Url`、`JsonSerializerOptions.IndentSize/NewLine`、`IReadOnlyList.Index()`、`ConfigureAwaitOptions`、`OperatingSystem.IsWindows`、`UnixFileMode`、`FileStreamOptions`、`ArgumentNullException.ThrowIfNull`、`Task.WaitAsync`、带 CancellationToken 的 `ReadAsStringAsync/ReadLineAsync` 等。
- 运行时：Unity Mono（不支持 IL2CPP 运行时注入）；前端 netstandard2.1、后端 net8.0。

## 九、质量约束

1. **可读优先**：命名表达意图，不用炫技写法；复杂处注释"为什么"，不注释"是什么"。
2. **可测优先**：Core 零 Unity/游戏引用；每个模块有单测；Faux provider 支撑无网测试。
3. **可解释优先**：讲不清的设计不写；写不出来讲解卡，说明还没想明白。
4. **不追求 1:1**：语义等价即可；C# 惯用法优先。
5. **不提前抽象**：先按模块落地，重复出现三次再抽公共件。
6. **不引入无关依赖**：每加一个包都要在决策日志说明理由。

## 十、节奏与讲解深度

- **流程分轨与模型路由**见 `docs/04-开发流程分轨与模型路由.md`：设计走重、移植走轻；强模型想，轻模型打。
- **批次节奏**：1–2 个模块为一批；每批结束做一次讲解 + 演示 + 复盘。
- **默认讲解深度**：关键决策 + 数据流 + 调优点（不逐行讲语法）。
- **"展开"**：用户说展开时，深入到源码级（原版 pi 文件/行号、C# 映射细节）。
- **"先做"**：用户说先做时，只保留决策点与风险，不展开教学。
- **复盘产出**：更新心智模型 + 调优手册 + 决策日志，而不是另开一堂课。

## 十一、反模式

1. 先看 Pi.NET 再看 pi（顺序反了）。
2. 把 Pi.NET 当行为标准，忽略它可能的偏离/缺陷。
3. 只读不跑：讲解卡没有对照验证。
4. 只跑不讲：代码能跑但说不出不变量和失败模式。
5. 讲解文档写成抄书/翻译，没有自己的理解。
6. 追求 1:1 移植，把 TS 的别扭结构搬进 C#。
7. 在 Core 里引用 Unity/GameData，破坏可测性。
8. 用 net9/net10 专有 API，导致 netstandard2.1 不可编。
9. 提前抽象：还没跑通就造"通用框架"。
10. 把"教学"变成额外负担，而不是交付物的一部分。
11. 以"用不到"为由删除公共类型/接口/字段（形状裁剪）。
12. 把"行为后置"写成"形状缺失"，用"范围边界"掩盖偏离。

## 十二、里程碑与阶段边界

### M1 · PiUnityAgent.Ai + PiUnityAgent.Core

- **交付**：pi-ai 全量公共类型/API/能力面（含 42 家 provider、OAuth、图片、classifier、deferred、嵌套工具调用、telemetry wire）；pi-agent-core 全量语义；Faux provider；一个真实工具；Unity 示例挂载；单测。
- **实现节奏**：核心类型/循环/两个主 provider 先行；其余 provider/feature 按阶段推进，**类型与能力面不删**。
- **不做（M1 暂不实现，但保留）**：Session 持久化、Compaction、Skills、扩展包加载（留给 2A）。
- **验收**：无网可跑；事件序列与 pi 对照语义一致；netstandard2.1 可编；未实现能力有明确 TODO/异常。

### 2A · PiUnityAgent.Runtime（agent 常用机制）

- **交付**：Session 树、Context 组装、Compaction、Extensions、Resources。
- **来源**：coding-agent 机制，不搬 CLI/TUI/编码工具。
- **验收**：长会话可用；分支/fork；压缩后可继续；扩展可注册工具/钩子。

### 2B · AI mod 常用功能（可选脚手架）

- **交付**：UI（F8/聊天/设置）、游戏钩子、记忆装配、诊断。
- **性质**：有观点、带 UI 依赖；**不塞进 Runtime**。
- **验收**：一个最小 AI mod 壳可跑；模块可拆装。
