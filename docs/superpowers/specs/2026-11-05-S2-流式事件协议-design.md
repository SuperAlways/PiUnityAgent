## 一、S2 在系统中的位置

S1 定义“最终消息长什么样”；S2 定义“这条消息正在生成时，如何按顺序流出来”。

```
Provider（S4/S5）
   │ 产生事件
   ▼
AssistantMessageEvent 流（S2）
   │ 消费者逐事件迭代：text_delta / toolcall_delta / ...
   ▼
Agent Loop（S7）
   │ 累积/等待终态
   ▼
AssistantMessage（S1）
```

S2 解决三件事：

1. **事件类型**：流式过程有哪些事件、各自携带什么；
2. **事件流容器**：生产者 `Push`、消费者异步迭代、`WaitForDone`；
3. **语义契约**：顺序、partial、终态、错误编码、计时、取消。

它不解决：HTTP 连接、SSE 分帧、provider 字段解析（那是 S3/S4/S5）。

## 二、范围

### 2.1 包含

- `AssistantMessageEvent` 及其 12 个变体；
- `AssistantMessageEventStream` / `IAssistantMessageEventStream`；
- 通用 `EventStream<TEvent, TResult>`；
- partial 快照、终态、取消、计时；
- 单测（事件顺序/等待/结束/取消/计时）。

### 2.2 不包含

- `StreamFn` 与 provider 调用（S3）；
- HTTP/SSE（S4/S5）；
- Agent Loop 的 turn 事件（S7）；
- 事件持久化/JSON 序列化（S10 只存消息，不存事件）。

## 三、事件类型（12 个变体）

对应 pi `types.ts:823-840`：

| 事件 | 字段 | 含义 |
|---|---|---|
| `start` | `Partial` | 流开始，携带首个部分消息 |
| `text_start` | `ContentIndex`、`Partial` | 文本块开始 |
| `text_delta` | `ContentIndex`、`Delta`、`Partial` | 文本增量 |
| `text_end` | `ContentIndex`、`Content`、`Partial` | 文本块结束（最终文本） |
| `thinking_start` | `ContentIndex`、`Partial` | 思考块开始 |
| `thinking_delta` | `ContentIndex`、`Delta`、`Partial` | 思考增量 |
| `thinking_end` | `ContentIndex`、`Content`、`Partial` | 思考块结束 |
| `toolcall_start` | `ContentIndex`、`Partial` | 工具调用块开始 |
| `toolcall_delta` | `ContentIndex`、`Delta`、`Partial` | 工具参数 JSON 增量 |
| `toolcall_end` | `ContentIndex`、`ToolCall`、`Partial` | 工具调用块结束 |
| `done` | `Reason`、`Message` | 正常终态 |
| `error` | `Reason`、`Error`（`AssistantMessage`） | 失败终态 |

### 3.1 C# 表示

采用 pi.net 的抽象 record + 嵌套 record：

```csharp
public abstract record AssistantMessageEvent
{
    public abstract string Type { get; }      // wire 名，便于日志/调试
    [JsonIgnore] public bool IsTerminal => this is Done or Error;
    public sealed record Start(AssistantMessage Partial) : AssistantMessageEvent;
    // ... 其余 11 个
}
```

- 每个变体的 `Type` 返回 wire 名（`start`、`text_delta`、`done` 等）；
- 事件是内存对象，**S2 不做 JSON 多态序列化**；若以后要落事件日志，另加 converter。

### 3.2 与 pi.net 的差异

| pi.net | 本 spec | 原因 |
|---|---|---|
| `TextDelta` 额外带 `Sequence` | **不带** | pi（原版）没有；顺序由流保证 |
| `ThinkingDelta` 额外带 `Sequence`、`Signature` | **不带**（`Signature` 留在 `ThinkingContent.ThinkingSignature`） | 对齐 pi（原版）；事件只带 delta |
| `ToolCallDelta` 额外带 `Index` | **不带** | pi（原版）只有 `ContentIndex` + `Delta` |
| `Error` 额外带 `ErrorMessage` | **不带**；错误文本在 `AssistantMessage.ErrorMessage` | 避免重复字段 |
| `Done`/`Error` 的 `Reason` 类型不受限 | `StopReason` + **校验**：Done ∈ {Stop, Length, ToolUse, Deferred}；Error ∈ {Error, Aborted} | 对齐 pi 的 Extract 约束 |

> 如果后续日志/调试确实需要 `Sequence`，再加，并记录为扩展字段；S2 先保持最小。

## 四、partial 语义

pi（原版）的 `partial` 是“共享的活消息”，会持续增长；pi.net 用不可变 record，每次事件都是新快照。

**本 spec 采用不可变快照**：

- 每个事件携带当时的 `AssistantMessage` 快照；
- `AssistantMessageEventStream.Partial` 指向最新快照；
- 下游（S7）只看当前事件/当前 `Partial`，不能假设它会原地变化；
- 代价：每事件分配一个新消息对象；收益：线程安全、可记录、无别名突变。

这是 C# 记录模型下的最小偏离；必须在 S2 教学/代码注释里写清楚。

## 五、事件流容器

### 5.1 通用 `EventStream<TEvent, TResult>`

参考 pi `EventStream` / pi.net `EventStream`：

- **单消费者**异步枚举（不承诺广播）；
- 生产者 `Push(event)`；终态事件到达时标记结束；
- `End(result)` 关闭流并完成 `WaitForResult`；
- `Fail(exception)` 以异常关闭（仅用于基础设施错误；模型错误仍编码为事件）；
- 流结束后 `Push` 被忽略；
- 线程安全：生产者可在后台线程；消费者在调用线程迭代。

实现选择：

| 方案 | 评价 |
|---|---|
| `System.Threading.Channels.Channel` | 线程安全、异步友好；需要 `System.Threading.Channels` 包；单消费者 |
| 手写 FIFO + 等待队列 | 无额外依赖；要自己处理并发/取消 |

**推荐 Channel**（贴 pi.net，性能/鲁棒性好）；`SingleReader = true`、`SingleWriter = false`、unbounded。

### 5.2 `AssistantMessageEventStream`

在通用流之上：

- `Partial`：最新快照（`Start` 前为 null）；
- `Push(event)`：更新 `Partial`；终态事件时计时并完成；
- `End(finalMessage)`：写终态并关闭；
- `WaitForDoneAsync(ct)`：等待终态消息；
- `IAssistantMessageEventStream : IAsyncEnumerable<AssistantMessageEvent>`。

### 5.3 计时

pi 的 `AssistantMessageEventStream` 在终态消息上写 `durationMs`：

- 若 `message.DurationMs` 已有值 → 不覆盖；
- 若 `message.Timestamp < streamStartedAt` → 视为“别处开始的响应”，不覆盖；
- 否则写 `Math.Max(0, round(monotonicNow - startedAt))`。

C# 适配：

- netstandard2.1 没有 `Stopwatch.GetElapsedTime`（.NET 7）→ 用 `Stopwatch.GetTimestamp()` 差值 / `Stopwatch.Frequency`；
- `AssistantMessage.DurationMs` 是 `int?`，写入时限制在 `int` 范围；
- 使用单调时钟，不用 `DateTime.Now`。

## 六、错误与终态

### 6.1 错误是事件，不是异常

- provider/网络失败 → `Error(StopReason.Error, assistantMessage)`；
- 用户取消 → `Error(StopReason.Aborted, assistantMessage)`；
- 正常结束 → `Done(StopReason.Stop/Length/ToolUse/Deferred, message)`；
- 流容器的 `Fail(exception)` 只用于**基础设施错误**（例如消费者被释放），不用于模型错误。

### 6.2 终态约束

- `Done` 的 `Reason` 不能是 `Error`/`Aborted`/`Pending`；
- `Error` 的 `Reason` 只能是 `Error`/`Aborted`；
- 由构造工厂或 `Validate` 辅助方法强制；单测覆盖。

### 6.3 结束后

- 终态事件是最后一个事件；
- 后续 `Push` 被忽略；
- `WaitForDoneAsync` 返回终态消息（Done.Message 或 Error.Error）。

## 七、取消与线程

| 事项 | 决定 |
|---|---|
| 取消 | `IAsyncEnumerable` 的 `CancellationToken` + `WaitForDoneAsync(ct)`；netstandard2.1 无 `Task.WaitAsync`，用 `Task.WhenAny` + `ct.Register` 实现 |
| 生产者线程 | 可后台线程；Channel 线程安全 |
| 消费者线程 | 调用线程；Unity UI 的 marshaling 由 Host 层负责，不在 S2 |
| `Partial` 可见性 | `volatile`/lock 保护；只读快照 |
| 背压 | unbounded Channel（贴 pi.net）；不做有界阻塞，避免 provider 线程卡死 |

## 八、测试计划

1. **事件类型**：12 个变体的 `Type` 和 `IsTerminal`；
2. **顺序**：`start → text_start → text_delta → text_end → done` 逐事件迭代顺序；
3. **等待**：无消费者时 `Push` 入队，消费者开始后按序收到；
4. **结束后**：`done` 后 `Push` 被忽略；`WaitForDoneAsync` 返回终态；
5. **错误**：`error` 终态；`WaitForDoneAsync` 返回错误消息；
6. **取消**：取消迭代/等待，不挂死；
7. **计时**：终态写入 `DurationMs`；已有值/旧时间戳不覆盖；
8. **partial**：每个事件后 `Partial` 为最新快照；
9. **终态约束**：非法 `Done`/`Error` reason 被拒绝；
10. **单消费者**：两个迭代器不承诺广播（文档 + 若有测试，验证不 panic）。

## 十一、开放问题

1. **单消费者 vs 广播**：S2 选单消费者；如果 S7 需要多个观察者，应在 Agent 层订阅事件，而不是让多个迭代器抢同一个流。
2. **事件日志序列化**：S2 不做；如果 S10 需要事件审计，另立 spec。
3. **`Sequence` / `Index` 扩展字段**：本 spec 按 pi（原版）省略；如果调试需要，后续加为扩展并记录。
4. **`System.Threading.Channels` 依赖**：需要加包；若 Unity 侧包冲突，退手写 FIFO（性能/复杂度待评估）。
