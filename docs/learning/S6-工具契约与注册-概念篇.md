## 1. 它解决什么问题

S1 定消息、S2 定流、S3 定 provider；S5 之后模型"会说话"了，但还**不能做事**。

没有 S6：

- 模型只能输出文本，不能提出"我要查角色状态 / 我要执行动作"；
- 工具没有统一契约，每个 mod 自己发明参数格式，校验和错误编码各写一套；
- 工具结果没有受众分流，UI 想要的数据和模型需要的数据挤在一条文本里；
- S7（Agent Loop）没有可消费的工具地基，S8（钩子）没有拦截点的形状。

S6 提供的骨架：

1. **AgentTool 契约**：工具定义的完整形状（模型用的字段 + UI/程序用的字段，一次定齐）；
2. **参数 schema**：JSON Schema 一份两用——模型理解 + 运行时校验；
3. **AgentToolResult**：执行结果的三通道分流（模型/UI/程序化调用方）；
4. **错误编码**：失败不抛炸进程，编码成 `isError` 结果让模型有机会调整。

## 2. 在系统中的位置

```
S7 Agent Loop
     │ 按 name 找工具 → 校验 → 执行 → 回写 toolResult
     ▼
AgentTool 契约（S6）          ← 本阶段：只定形状 + 校验/错误编码
     │ execute
     ▼
宿主工具实现（S13 / 游戏mod）  ← 我们的工具：游戏查询/动作，不是 read/bash/edit
```

S6 只负责契约段。链路其余环节各有归属：

| 环节 | 归属 |
|---|---|
| 循环调度、并行/串行、回写顺序 | S7 |
| before/after 钩子、steer/followUp 队列 | S8 |
| system prompt 里的工具准则（promptSnippet/promptGuidelines） | S9 |
| ResourceLoader / registerTool 动态注册 | S12 |
| 具体游戏工具实现 | S13 + mod |

**S6 的纪律**：形状一次到位（S7/S8/S13 直接消费，不改契约），行为可后置。

## 3. 工具是一份契约，不只是一个函数

最小四件套支撑 ReAct 循环（推理→行动→观察→再推理）：

| 字段 | 给谁 | 作用 |
|---|---|---|
| `name` | 模型（调用）+ UI | 稳定名字 |
| `description` | **只给模型** | 什么时候该调、边界在哪 |
| `parameters` | 模型 + 校验器 | JSON Schema，一份两用 |
| `execute` | 运行时 | 真正干活，只有宿主能调 |

v1.5.0 真实契约比最小四件套厚（细节见源码篇）：`label`（UI 显示名，与 description 分受众）、`prepareArguments`（校验*前*的参数兼容垫片）、`outputSchema`+`structuredContent`（程序化调用方）、`isError`/`terminate` 信号位、`onUpdate` 流式汇报。

**"契约"的含义**："工具成功"本身要定义准确——写工具返回成功只证明写入完成，不证明程序按新配置运行；搜索返回空只证明当前条件下没找到。契约写不清，模型会做跨越证据的推断。

## 4. 三个收件人、三个通道（Q&A 核心）

不是"一份数据两套渲染"，而是**字段定义时就分好受众**：

| 通道 | 字段 | 约束 |
|---|---|---|
| **模型** | `content` | 进历史永久占 token；发送时冻结；必须自包含 |
| **UI** | `details`、`label`、`onUpdate` | 便宜、可实时更新、可结构化、可事后重渲染 |
| **程序化调用方** | `structuredContent` | 机器可读，不进模型不归 UI |

设计口诀：**"模型下一步决策需要这条信息吗？需要 → content；只是人想看 → details。"**

谁生产 ≠ 给谁，两个独立维度：LLM 在工具环节只生产"调用意图"（工具名+参数）；结果 content/details 是**工具代码**写的。

## 5. 错误也是工具结果

工具不存在、参数校验失败、被 hook 阻止、execute 抛异常——都不炸进程，统一编码成 `isError: true` 的 toolResult，模型看到错误文本、有机会调整计划。理由：模型犯错是常态，错误是它的输入；异常炸掉等于一错就死。pi 两条路通向同一终点：主动返回 `isError`（保留 details 给 UI）或抛异常（loop 捕获转 error toolResult），对模型长得一样。

## 6. 并行与串行（概念先立，实现归 S7）

一条助手消息可带多个 toolCall：**执行可并发，回写按原始调用顺序**（否则模型看到错乱上下文）。只读可并行、有副作用要串行是策略，由上层决定。

## 7. 落到我们

- pi 内置工具（read/bash/edit/grep）是编码场景，路线图 §四明确暂不做；我们的工具是游戏查询/动作；
- S6 移植的是契约骨架，具体游戏工具是 S13 + mod 的事；
- 资源加载/动态注册属 S12，S6 只做契约与静态注册的形状。

## 8. Q&A（阶段 0 问答记录）

**Q：对 LLM 上下文一套、对 UI 另一套——工具名描述等是写死的原始内容，LLM 只生成一部分，为什么要做不一样的设计？**

A：不是同一份数据两套渲染，而是字段定义时就分了受众。声明层：`description`（只给模型）与 `label`（只给 UI）分开就是证据。结果层：`content`（模型，进历史永久占 token、发送时冻结、必须自包含）与 `details`（UI，便宜、可实时更新、可结构化）与 `structuredContent`（程序化调用方）三分。谁生产 ≠ 给谁：LLM 只生产调用意图（工具名+参数），结果 content/details 是工具代码写的。反例代价：把 DTO 塞进 content = 模型注意力被垃圾淹没 + 每轮重发；只给 content 不给 details = UI 被迫解析中文文本。

**Q（确认理解）：S6 是设计 Agent 工具格式——除支持 LLM ReAct 的必需字段外，也对 UI、其他 trace 暴露接口字段，方便人或其他 Agent 查看 ReAct 过程？**

A：方向正确。两点钉子：① 最小四件套支撑 ReAct 循环；② 对外暴露字段（details/structuredContent/label/onUpdate）在 S6 定的是**形状**，真正的过程可见（事件流、update 推送）是 S7/S8 的行为——S6 保证届时不用改契约就能接上（"形状不可裁剪、行为可后置"）。
