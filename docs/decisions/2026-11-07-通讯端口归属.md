# 决策 · 通讯端口归属（B 方案）

> **日期**：2026-11-07
> **状态**：已接受（用户 2026-11-07 拍板 B）
> **相关**：[07-通讯层集成契约](../07-通讯层集成契约.md) · [S3 返工 spec v2](../superpowers/specs/2026-11-07-S3-对齐返工-design-v2.md) · [UnityLlmTransport Phase 2 结果](../../../UnityLlmTransport/docs/spike/phase2-results.md)

## 一、背景

S3 形状返工时发现 `StreamOptions` 只有 `HttpClient?` 一个 HTTP 注入点，而 Unity 主路径的传输是 `UnityLlmTransport` 的 UWR（`IStreamingHttpTransport`），两者对不上。需要决定：**传输端口归谁所有？**

- 原 `UnityLlmTransport/README.md` 写的依赖方向是 `PiUnityAgent.Ai → UnityLlmTransport.Abstractions`（A 方案）。
- pi 原版把 `fetch?: FetchFunction` 定义在 `packages/ai/src/types.ts`（协议包自有端口）；pi.net 则是 `HttpClient?` 参数。
- UnityLlmTransport Phase 2（2026-11-07）已完成：3 版本 × Mono/IL2CPP，6 组 15/15，`Abstractions` 契约稳定。

## 二、决策

**采用 B 方案：**

1. `PiUnityAgent.Ai` 自己定义 `FetchFunction` / `FetchRequest` / `FetchOptions` / `IFetchResponse` / `FetchException` / `TransportKind`；
2. `PiUnityAgent.Ai` **不引用** `UnityLlmTransport`、`UnityEngine` 或任何具体传输；
3. `UnityLlmTransport` 通过 `PiUnityAgent.Hosts.Unity`（或 `Ext.Transport.UnityLlmTransport`）的适配器消费；
4. 适配器负责 `Fetch 端口 ↔ IStreamingHttpTransport` 的双向映射；
5. 通讯事实以 `UnityLlmTransport/docs/` 为准；协议事实以 `PiUnityAgent/docs/` 为准。

## 三、理由

1. **形状对齐 pi 原版**：pi 的 `fetch` 是 `ai` 包公共类型，注入点在 `StreamOptions`；B 方案是它最直接的 C# 等价。
2. **Ai 保持自包含**：`PiUnityAgent.Ai` 当前只依赖 `System.Text.Json`；引用外部 Abstractions 会让协议层的公共 API 被另一仓库的版本牵着走。
3. **传输组件真正可替换**：任何通讯实现（UnityLlmTransport、其他组件、自写 UWR 封装）都通过适配器接入，不被 `IStreamingHttpTransport` 绑死。
4. **两个仓库解耦**：PiUnityAgent 的公共端口稳定；UnityLlmTransport 的 `Abstractions` 可继续按自己的 0.x 节奏演进，只需适配器跟踪。
5. **代价可控**：适配器只在 Host 层（S13/S4）出现，约一个类 + 契约测试；不进入 Ai/Core/Runtime。

## 四、被否决的 A 方案

`PiUnityAgent.Ai → UnityLlmTransport.Abstractions` 直接依赖。

- 优点：少一层适配、契约只有一份、落地最快。
- 否决原因：Ai 的公共 API 依赖兄弟仓库版本；“选择其他通讯组件”需要对方实现同一接口；开源分发时 Ai 多一个外部包依赖。
