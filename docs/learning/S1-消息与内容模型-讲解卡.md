## 1. 它解决什么问题

模型只认四种角色：`system`、`user`、`assistant`、`toolResult`。
但一个真实 agent 还需要表达：文本、思考、图片、工具调用、工具结果、用量、停止原因、错误。

**消息与内容模型就是这层"共同语言"**：

- 它让 provider 能按各自协议发送/解析；
- 让 agent loop 能读懂"模型要调哪个工具"；
- 让会话/压缩/日志能稳定序列化。

如果没有它，每个 provider、每个工具、每个会话格式都会各造一套结构。

---

## 2. 数据流 / 状态机

```
SystemMessage（可带 sections / toolsAdded / toolsRemoved）
        │
        ▼
UserMessage（string 或 Text/Image 内容块）
        │
        ▼
AssistantMessage（Text / Thinking / ToolCall 内容块 + usage + stopReason）
        │
        ├─ 无 ToolCall → 本轮结束
        └─ 有 ToolCall
                │
                ▼
        ToolResultMessage（toolCallId + toolName + content + isError）
                │
                ▼
        下一轮 AssistantMessage
```

`Message` = 这四种的联合：
`Message = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage`

**`Context` vs `TranscriptContext`**（重要）：

- `Context`：调用方输入，允许用 `systemPrompt` / `tools` 简写；
- `TranscriptContext`：规范化后的请求上下文，system prompt 与工具声明已经折进 **system message**；
- 只有 `normalizeContext()` 能产出 `TranscriptContext`，防止原始 `Context` 直接进 provider。

---

## 3. 三条关键不变量

1. **角色与内容块匹配**
   - `system`：`string | TextContent[]`，可带 `sections`、`toolsAdded`、`toolsRemoved`；
   - `user`：`string | (TextContent | ImageContent)[]`；
   - `assistant`：只能是 `TextContent | ThinkingContent | ToolCall`；
   - `toolResult`：必须有 `toolCallId`、`toolName`、`content`、`isError`。

2. **工具结果必须能追溯到工具调用**
   - `ToolResultMessage.toolCallId` 必须对应某个 `ToolCall.id`；
   - 不允许出现"没有调用方的工具结果"；
   - 工具结果的内容是给模型看的，`details` 是给 UI/日志看的，二者不要混。

3. **失败是数据，不是异常**
   - 模型/网络失败：`stopReason = "error" | "aborted"` + `errorMessage`；
   - 工具失败：`isError = true`，而不是抛到循环外；
   - 参数 JSON 坏：`ToolCall.argumentsError` 有值，`arguments = {}`；
   - 截断：`stopReason = "length"`；
   - 推理内容：`ThinkingContent.redacted` 表示被安全过滤，签名仍在 `thinkingSignature`。

---

## 4. 失败模式

| 场景 | 表现 | 我们要怎么处理 |
|---|---|---|
| 模型返回坏 JSON 工具参数 | `ToolCall.argumentsError` 有值，`arguments = {}` | 校验失败 → 作为错误 toolResult 回给模型 |
| 请求被中止 | `stopReason = "aborted"` | 不重试；保留已产生的消息 |
| 输出被截断 | `stopReason = "length"` | 记录；S11 压缩/重试再处理 |
| provider 报错 | `stopReason = "error"` + `errorMessage` | 编码为消息/事件，不抛到调用方 |
| thinking 被安全过滤 | `ThinkingContent.redacted = true` | 保留签名，按 provider 规则回放 |
| 工具结果缺 `toolCallId` | 非法消息 | 构造层直接拒绝/断言 |
| 空 content | 合法但无用 | 上层决定是否重试；类型层不禁止 |

## 5. 事件顺序（S1 只到消息，S2 再讲流式）

消息层只关心"最终消息"的顺序：

```
system → user → assistant → toolResult → assistant → ...
```

流式事件（`assistant_start/text_delta/...`）属于 S2；S1 不实现事件流，但类型要为 S2 留好 `AssistantMessage` 与 `ToolCall`。

## 6. 可调旋钮

| 旋钮 | 影响 | 备注 |
|---|---|---|
| `maxTokens` | 单次输出上限 | `Model.maxTokens` / 请求选项 |
| `thinkingLevel` | 推理预算 | `off`…`max`；provider 可能不支持 |
| `samplingParams` | 温度/采样 | 模型默认 + 请求覆盖 |
| `toolChoice` | 是否允许/强制工具 | `auto` / `none` |
| `stopReason` 处理策略 | 是否重试/压缩 | 由 agent loop 决定，不在类型层 |

## 7. TS → C# 映射

| TS | C# |
|---|---|
| `Message` 联合 | `abstract record Message` + `SystemMessage` / `UserMessage` / `AssistantMessage` / `ToolResultMessage` |
| `TextContent | ThinkingContent | ImageContent | ToolCall` | `abstract record ContentBlock` + 四个派生 record |
| `content: string \| ...[]` | 用一个 `MessageContent` 抽象或显式重载；不要用 `object` |
| `Record<string, string \| null>` | `IReadOnlyDictionary<string, string?>` |
| `JsonObject` | `System.Text.Json.Nodes.JsonObject` 或自定义 `JsonValue` |
| `number`（时间戳） | `long`（Unix ms） |
| `Usage.cost` 嵌套对象 | `UsageCost` record |
| `ToolResultMessage<TDetails>` 条件类型 | 泛型 `ToolResultMessage<TDetails>`；C# 不需要条件类型 |
| 可选字段 `?` | `T?` / nullable |
| 字符串字面量联合（`stopReason`） | `enum StopReason` + wire name 映射 |

**命名规则**：类型名与上游一致；C# 只做 PascalCase、`Async` 后缀、`I` 前缀、union→record 的机械变换。

## 8. 与 Pi.NET 的差异

- Pi.NET 已有一份 C# 类型（`Pi.Ai.Types`），可作为"写法参考"：
  - 它用 record/抽象类表达联合；
  - 它可能为了 net9/10 做了简化或额外字段。
- 我们**不照抄**它的字段/命名；以 v1.5.0 `types.ts` 为准。
- 差异记录到 `PORTING.md` 与决策日志。

## 10. 验证方式

S1 的测试（不依赖网络）：

1. **构造/序列化**：四种消息 round-trip，字段不丢。
2. **联合类型**：`AssistantMessage.content` 只接受 text/thinking/toolCall；toolResult 必须带 `toolCallId`。
3. **工具调用链**：`ToolCall.id` ↔ `ToolResultMessage.toolCallId` 的配对校验。
4. **用量/停止原因**：`Usage` 的 total/cost 字段；`StopReason` 枚举与 wire name 映射。
5. **失败编码**：坏参数 → `argumentsError`；abort → `stopReason=aborted`；length → `stopReason=length`。
6. **与 Pi.NET 对照**：同一组消息在两边序列化，结构语义一致（不要求字段顺序一致）。

下一阶段 S2 再用 Faux provider 验证流式事件。
