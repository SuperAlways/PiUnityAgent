## 1. 先看完整链路

一条用户输入，在 agent 系统里大致这样走：

```
玩家/宿主
   │ 输入
   ▼
UserMessage ──────────────┐
                          │
SystemMessage ────────────┤  transcript（模型看到的上下文）
                          │
AssistantMessage ◄────────┘
   │ 文本 / 思考 / 工具调用
   ▼
工具执行层
   │ 工具结果
   ▼
ToolResultMessage
   │
   ▼
下一轮 AssistantMessage
```

S1 不负责这条链路的"跑"；它负责定义链路上**每一站的数据形状**。

---

## 2. 这一层解决什么问题

如果没有 S1：

- 每个 provider 自己定义消息；
- 每个工具自己定义结果；
- 每个会话格式自己决定怎么存；
- agent loop 要在多种形状之间来回转换。

S1 把"模型输入/输出的共同语言"固定下来：

- **模型能看到什么**：system / user / assistant / toolResult；
- **模型能返回什么**：文本、思考、工具调用；
- **工具结果怎么表达**：toolCallId、content、isError；
- **一次响应怎么计量**：usage、stopReason、error。

一句话：**S1 是 agent 的语法和词汇。**

---

## 3. 四种角色

| 角色 | 由谁产生 | 主要内容 | 在链路里的作用 |
|---|---|---|---|
| **system** | 宿主 / agent | 规则、prompt、工具声明 | 告诉模型"你是谁、能做什么" |
| **user** | 玩家 / 宿主 | 文本、图片 | 输入 |
| **assistant** | 模型 | 文本、思考、工具调用 | 输出 |
| **toolResult** | 工具执行层 | 文本/图片、toolCallId、isError | 把工具结果回给模型 |

关键：这不是"聊天记录"，而是**模型请求的完整上下文**。system 和 toolResult 都在里面。

---

## 4. 内容块矩阵

一条消息的内容不是一个字符串，而是"块"：

```
ContentBlock
├─ TextContent       文本
├─ ImageContent      图片
├─ ThinkingContent   思考
└─ ToolCall          工具调用
```

不同角色允许的块不同：

| 角色 | 文本 | 图片 | 思考 | 工具调用 |
|---|---|---|---|---|
| system | ✅ | ❌ | ❌ | ❌ |
| user | ✅ | ✅ | ❌ | ❌ |
| assistant | ✅ | ❌ | ✅ | ✅ |
| toolResult | ✅ | ✅ | ❌ | ❌ |

这张表是 S1 最重要的不变量之一。

---

## 5. 工具调用与工具结果是一对

```
assistant:
  Text("我先查一下")
  ToolCall(id = call_1, name = query_injuries)
        │
        ▼
toolResult:
  toolCallId = call_1
  toolName = query_injuries
  content = [Text("左臂旧伤")]
  isError = false
```

规则：

- `toolResult.toolCallId` 必须对应某个 `ToolCall.id`；
- 没有调用方的工具结果 = 非法消息；
- 一个 assistant 消息可以有多个工具调用；
- 工具结果按调用顺序配对，但执行可以并行。

## 6. Context vs TranscriptContext

这是最容易忽略、但 S9 会反复用到的区分：

```
Context（调用方输入）
  系统提示 + 消息列表 + 工具列表
        │
        │ 规范化
        ▼
TranscriptContext（模型真正收到的）
  messages: [
    SystemMessage（prompt + 工具声明）,
    UserMessage,
    AssistantMessage,
    ToolResultMessage
  ]
```

- **Context** 允许简写"系统提示 / 工具"；
- **TranscriptContext** 里，它们已经折进 system 消息；
- 只有规范化函数能产出 `TranscriptContext`，防止原始 `Context` 直接进 provider。

## 7. 失败是数据，不是异常

| 失败 | 在消息里怎么表达 |
|---|---|
| 模型/网络失败 | `stopReason = error/aborted` + 错误文本 |
| 工具失败 | `isError = true` + 错误内容 |
| 工具参数坏 | `argumentsError` 有值，`arguments` 为空 |
| 输出被截断 | `stopReason = length` |
| 推理被安全过滤 | `redacted = true`，签名保留 |

为什么？因为 agent loop 需要**看到失败并决定下一步**，而不是被异常打断。

## 8. 图片怎么存（你问过的问题）

图片在消息对象里**不是二进制**，而是：

```
原始图片字节
   │ base64 编码
   ▼
纯文本字符串 + mimeType
   │
   ▼
ImageContent { data, mimeType }
```

- `data` 是 base64 字符串；
- `mimeType` 说明格式；
- 体积比原始字节大约 +33%；
- 会话文件会跟着变大；
- 日志不能原样打印 `data`。

图片只出现在 **user** 和 **toolResult**；system 和 assistant 不带图片。

## 9. 常见误区

1. **"消息就是聊天记录"**：agent 消息还承载工具调用、工具结果、思考、usage。
2. **"system 就是一段 prompt"**：它还承载工具声明和 prompt 分段，后续 system 消息可以增量修改。
3. **"工具结果就是普通消息"**：它必须能追溯到某个工具调用。
4. **"失败就抛异常"**：agent 里失败要变成数据，交给上层决策。
5. **"S1 只是类型定义，不重要"**：它是所有下游的接口；S1 形状错了，S2–S13 都要改。

## 10. 和 pi 系统的对应

| 阶段 | 和 S1 的关系 |
|---|---|
| **S2 流式事件** | 描述 assistant 消息"正在生成"的过程 |
