## 2. 核心类型关系

```
Context
  systemPrompt? + messages + tools?
        │
        │ normalizeContext()  [transcript.ts:30]
        ▼
TranscriptContext
  messages: Message[]
        │
        │ provider（S4/S5）
        ▼
AssistantMessageEvent 流（S2）
        │
        ▼
AssistantMessage
  content: Text / Thinking / ToolCall
        │
        │ 有 ToolCall
        ▼
ToolResultMessage
  toolCallId + content + isError
        │
        ▼
下一轮 AssistantMessage
```

**`Message` 是 type union，不是运行时基类。** 运行时是四种具体对象。

### 3.1 `SystemMessage` 不只是 prompt

```ts
// types.ts:561
export interface SystemMessage {
  role: "system";
  content: string | TextContent[];
  sections?: Record<string, string | null>;
  toolsAdded?: Tool[];
  toolsRemoved?: ToolReference[];
  timestamp: number;
}
```

- `content` **必填**；
- `sections` 按名增量修改 prompt；
- `toolsAdded` / `toolsRemoved` 让工具集增量变化；
- 后续 system 消息可以“补丁式”修改前面的 prompt。

### 3.2 `ToolCall` 的失败是数据

```ts
// types.ts:444
argumentsError?: string; // 模型参数不是合法 JSON 时置位，arguments 为 {}
```

### 3.3 `ToolResultMessage` 的条件泛型

```ts
// types.ts:640
export type ToolResultMessage<TDetails = JsonValue> =
  IsJsonCompatible<TDetails> extends true
    ? { ...; details?: JsonRepresentation<TDetails>; ... }
    : never;
```

运行时 `details` 就是一个 JSON 值；泛型只是编译期约束。

### 4.1 `normalizeContext`（:30）

```ts
export function normalizeContext(context: Context): TranscriptContext {
  const initialMessage = createInitialSystemMessage(context.systemPrompt, context.tools);
  const messages = initialMessage ? [initialMessage, ...context.messages] : context.messages;
  return { messages } as TranscriptContext;
}
```

唯一职责：**把简写的 systemPrompt/tools 折成首条 system 消息**。

### 4.2 `getCurrentTools`（:58）

按顺序遍历 transcript 里的 system 消息：

- 先删 `toolsRemoved`；
- 再加 `toolsAdded`；
- 返回当前工具集。

### 4.3 `getCurrentSystemMessage`（:73）

回放所有 system 消息：

- `content` 追加；
- `sections` 按名替换，`null` 删除；
- 工具用 `getCurrentTools` 合并；
- 返回“当前完整 prompt + 工具”。

S9 上下文组装会重度依赖它。

### 4.4 `collapseSystemMessages` / `resolveTranscript`（:108/:115）

有些 provider 不接受中途 system 消息：

- `collapseSystemMessages` 把后续 system 折叠进首条；
- `resolveTranscript` 根据 provider 能力选择保留还是折叠。

## 7. pi.net 的对应实现

| pi（原版） | pi.net | 差异 |
|---|---|---|
| `TextContent` / `ImageContent` / `ThinkingContent` / `ToolCall` | `Pi.Ai/Types/Messages.cs`：`TextContent`、`ImageContent`、`ThinkingContent`、`ToolCallContent` | `ToolCallContent` 命名偏离；`Signature` 对应 `thinkingSignature` |
| `ContentBlock` 联合 | 抽象 record + `JsonPolymorphic`/`JsonDerivedType` | STJ 多态特性 |
| `string \| blocks` | `MessageContent` 包装类型 + 自定义 converter | 匿名联合 → 具名包装 |
| `StopReason` 字符串联合 | enum + `JsonStringEnumMemberName` | .NET 9 特性；我们需自定义 converter |
| `ToolResultMessage<T>` | 非泛型 + `object? Details` | 条件泛型 → 非泛型 |
| `Context` / `TranscriptContext` | `Pi.Ai.Types` 对应 | 形状基本一致 |

**结论**：pi.net 是 C# 形状参考，但命名和 .NET 版本特性要按 pi（原版）+ netstandard2.1 校正。

## 8. 常见误区

1. 把 `Message` 当运行时基类——它只是 TS 类型联合。
2. 把 `SystemMessage.content` 当可选——上游必填。
3. 忽略 `sections` / `toolsAdded` / `toolsRemoved`——system 消息可增量修改 prompt 和工具集。
4. 把 `Context` 直接传给 provider——必须先 `normalizeContext`。
5. 认为 `ToolResultMessage<T>` 运行时带泛型——运行时就是普通 JSON 对象。
6. 把 `details` 当模型可见内容——模型只看 `content`。
