## 一、为什么需要它

### 1.1 现状

《太吾绘卷》及同类 Unity 游戏里，AI mod 已经形成一个小生态：

| 项目 | 定位 | 现有底座 |
|---|---|---|
| 太吾药老 | 游戏内 F8 问答助手（百晓册 + LightRAG） | 自研 ReAct 循环，C# |
| 江湖有灵 | NPC 真办事 + 过月演化 + 江湖大事 | 自研三层（Frontend/Core/Backend） |
| WorldTalk | NPC 闲谈 + 飞鸽 + 人格画像 | 自研两层 + ActionTool |
| 说书人 | 感知 + 导演 + 呈现（叙事） | 感知管线已有，agent 层待建 |

四家的**底座级能力高度重合**：LLM 调用、流式、工具调用、会话/记忆、上下文压缩、技能加载、扩展注册、后台/过月调度。每家都自己造了一遍，质量和 API 各不相同。

### 1.2 机会

把"底座"抽出来，形成一个**平台无关的 C# agent 底座**：

- 新 mod 不用再从零写循环、重试、压缩、工具协议；
- 已有 mod 可以逐步迁移，把精力放回"业务"；
- 扩展作者只面对 `IExtension`，不关心进程、线程、传输；
- 同一份 Core 同时服务"主流 Unity 单进程游戏"和"太吾双进程游戏"。

| pi 组件 | 内容 | 规模 |
|---|---|---|
| `pi-agent-core` | Agent Loop、Agent 状态、steering/follow-up、传输抽象 | 约 2,519 行 TS |

- 无权限系统的"全能 agent"默认姿态；游戏写操作必须走白名单 + 回读 + 幂等。
- Node 生态的运行时与包管理。

## 三、目标框架与兼容范围（已核实）

### 3.1 现有项目的实际 TFM

| 项目 | Frontend / Core | Backend |
|---|---|---|
| 太吾药老 | Core `netstandard2.1` | `net8.0` |
| 说书人 | `netstandard2.1` | `net8.0` |
| WorldTalk | `netstandard2.1` | `net8.0` |
| 江湖有灵 | **`.NET Framework 4.8`** | `net8.0` |

### 3.2 太吾本体（实测）

| 项 | 值 | 证据 |
|---|---|---|
| Unity 版本 | 2022.3.62f2 | `UnityPlayer.dll` ProductVersion |
| 前端运行时 | Unity Mono（Managed 下有 mscorlib + netstandard） | 游戏 `_Data/Managed/` |
| 后端运行时 | .NET 8.0.22（自带 hostfxr，独立进程） | `Backend/GameData.runtimeconfig.json` |

### 3.3 Unity 兼容范围

| Unity 版本 | netstandard2.1 |
|---|---|
| 2021.2 – 2021.3 LTS | ✅（2.1 从此版本开始支持） |
| 2022.1 – 2022.3 LTS（含太吾） | ✅ |
| Unity 6（6000.x） | ✅（仍以 2.1 为默认；CoreCLR 进度待核实） |
| 2020.3 LTS 及更早 | ⚠️ 只有 .NET Standard 2.0，不保证 |

**结论**：Core 用 `netstandard2.1`。它是"Unity 2021.2+ 前端"与"太吾 .NET 8 后端"的共同分母；net48 虽然能在太吾跑，但不可移植、且后端引用不干净。

**前置条件**：

1. 必须是 Mono 后端（IL2CPP 不能运行时注入程序集）。
2. 看游戏的 Api Compatibility Level；netstandard2.1 比 net48 更安全。
3. TFM 是编译期契约，Unity 实现有少量差异，以目标游戏实测为准。

## 四、分层与职责

```
扩展层（各 mod 业务）
    ▲ 只依赖接口
宿主适配器（Host）
    ├─ Unity Host：主线程 Dispatcher、UnityWebRequest SSE、UGUI 事件
    └─ .NET 8 Host（可选）：HttpClient SSE、后台任务、ALC 扩展加载
    ▲ 引用
PiUnityAgent.Ai + Core + Runtime（netstandard2.1，纯逻辑）
    └─ 消息/工具契约、Agent Loop、会话树、压缩、技能、provider 抽象
```

### 4.1 Core（本体层）

- 零 `UnityEngine` / 零游戏 API / 零进程假设；
- 必须有单测；
- 对外只暴露：消息类型、工具契约、事件流、`IAgentHost` / `ITransport` / `IToolExecutor`。

### 4.2 Hosts（胶质层）

| Host | 职责 |
|---|---|
| `PiUnityAgent.Hosts.Unity` | UnityWebRequest SSE、主线程 Dispatcher、文件存储、UI 事件桥 |
| `PiUnityAgent.Hosts.Net8` | HttpClient SSE、后台任务、ALC 扩展加载、RPC 服务 |

### 4.3 扩展（业务层）

- `IExtension` 注册工具、命令、事件钩子、context transform；
- 工具声明执行位：`InProcess` / `Unity` / `UnityMainThread` / `Backend` / `Http`；
- 扩展作者不感知进程边界，底座负责路由。

## 五、硬约束

| # | 约束 | 说明 |
|---|---|---|
| C1 | Unity 兼容 | Core 必须能在 netstandard2.1 / Unity Mono 下跑 |
| C2 | 零/轻依赖 | 优先零依赖；可合并进 mod DLL |
| C3 | 无 Node/Python 运行时 | 终端用户不应额外安装运行时 |
| C4 | 流式 + 工具调用 | 必须支持 SSE 与 function/tool calling |
| C5 | 主线程分离 | 游戏 API 只能在 Unity 主线程；工具执行可路由 |
| C6 | 可单测 | Core 纯逻辑，无 Unity 环境可测 |
| C7 | 许可证可用 | MIT/Apache 等允许免费 mod 分发 |
| C8 | 可打包 | 能进 Plugins，体积可接受；IL2CPP 需评估 |
| C9 | 多 provider | 至少 OpenAI-compatible + Anthropic |
| C10 | 可扩展 | 第三方可注册工具/技能，不改 Core |

## 六、能力清单

### P0（没有就不是底座）

1. 统一消息模型（文本/工具调用/推理内容/多段 content）
2. 统一流式事件（text/reasoning/tool call/usage/done）
3. Provider 抽象（OpenAI-compatible + Anthropic）
4. Agent Loop（组装 → 调用 → 工具 → 回写 → 继续/结束，可中止）
5. 工具注册与执行（schema、执行位、超时、错误回传）
6. 会话持久化（至少线性 JSONL，理想是树形）
7. 上下文压缩（摘要条目替换旧消息，原文保留）
8. 技能按需加载（先摘要后全文）
9. 重试与降级（退避、超时、失败不阻塞游戏）
10. Core 纯逻辑可单测

### P1

11. 扩展生命周期（tools/commands/hooks/context transform）
12. 多 agent 编排接口
13. token 估算与预算
14. JSON Schema 约束与防幻觉
15. provenance 挂点（事实/叙述/追认）

### P2

16. RAG/向量
17. 多模态
18. 本地模型
19. 可观测性（trace/cost）

## 七、非目标

- 不做终端 UI、代码编辑、bash 工具；
- 不做云端服务、多租户、鉴权；
- 不做具体某个 mod 的业务（叙事、问答、NPC 行为）；
- 不默认开放文件/进程/网络权限；
- 不依赖 Node/Python 运行时。

## 九、验收标准（框架级）

1. 新 mod 只写 `IExtension` 就能获得：多 provider、流式、工具、会话、压缩、技能。
2. 同一扩展不改代码，在单宿主与双宿主下都能运行。
3. Core 单测全绿，且不引用 Unity/游戏。
4. 游戏更新时只动 Host 适配层，Core 与扩展零改动。
5. 游戏写操作全部经过白名单 + 回读 + 幂等，失败可降级。
