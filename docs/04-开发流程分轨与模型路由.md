# 04 · 开发流程分轨与模型路由（2026-11-05）

> **状态**：流程约定 v1。
> **用途**：回答两件事：① 什么工作走重流程、什么走轻流程；② 什么工作用什么模型，怎么控制成本。
> **上游**：`docs/03-开发方法-拆解学习与移植约定.md`（方法论）；本文是执行层的分轨与路由。
> **一句话**：**设计走重、移植走轻；强模型想，轻模型打；失败升级，不原地重试。**

---

## 一、为什么分轨

superpowers 全套（brainstorming → spec → plan → SDD）解决的是"设计不确定"。
但移植型工作的不确定性在**上游 pi**里，不在我们这里：

- 行为、事件顺序、失败模式、边界都由原版 pi 定义；
- 再做一遍 brainstorming/spec，等于把已经想清楚的东西重新讨论一遍；
- 真正需要重流程的是：扩展模型、Unity 线程、Session/Compaction 语义、权限与安全。

所以按工作类型分轨，而不是全项目一刀切。

---

## 二、三类工作与流程

| 类型 | 特征 | 流程 | 模型档位 |
|---|---|---|---|
| **A. 设计型** | 没有现成答案：扩展模型、Unity 主线程、会话/压缩语义、权限 | brainstorming → spec → writing-plans → SDD | **强模型全程** |
| **B. 移植型** | 行为由原版 pi 定义：消息、事件流、Agent Loop、工具执行 | 教学型 brainstorming → spec → plan → subagent + Haiku 搬运 → 对照 → 教学 → 门禁 | **强模型讲解/审查 + Haiku 搬运** |
| **C. 探索型** | 不知道能不能做：ALC、IL2CPP、SSE、RPC 桥 | time-box spike → 决策日志 → 归入 A 或 B | **强模型判断 + Haiku 搭环境** |

M1（Ai + Core）绝大多数是 **B**；2A 的 Session/Compaction 取舍是 **A**；Unity 宿主是 **C → A/B**。

## 三、B 轨轻流程（M1 默认）

```
同步参考源 + 版本卡（sop/02）
  → 读 pi（原版）
  → 阶段 0：宏观概念讲解（无代码）→ 你提问 → 概念篇
  → 阶段 1：pi 源码导读（模块/文件/函数）→ 你提问 → 源码篇
  → 阶段 2：每个差距按 pi（原版）→ pi.net → Unity/2.1 硬约束 → 最小偏离推荐（性能/鲁棒性）→ spec（用户 review）
  → 阶段 3：plan（writing-plans）→ subagent + Haiku 搬运 → 强模型审查 → 对照/门禁
  → 阶段末：教学篇 + 学习问答记录 + 更新 PORTING.md
  → 一次 review（自己或 reviewer agent）
  → 门禁
```

> **第一阶段必须有教学型 brainstorming**：先宏观概念（无代码）→ 用户提问 → 概念篇；再 pi 源码导读（有代码）→ 用户提问 → 源码篇；最后才做实现设计与 spec。不是问需求、不是直接给方案。
> **判断标准**：下游零适配优先；只有硬约束才偏离，偏离必须记录代价。brainstorming 结束前不改代码、不写 plan。
> **阶段一对齐铁律（docs/03 §1.3）**：形状与行为以 pi 原版为准；语言/生态差异借 pi.net；只有 Unity/netstandard2.1 硬约束可取舍。行为可后置，**形状不可缺**；spec 必附三方偏离表。

**去掉**：brainstorming、完整 spec、SDD 多轮派发、任务 brief 生成。
**保留**：TDD、对照验证、讲解卡、教学文档、门禁。

## 四、模型路由表

> 本环境 Agent 工具的 `model` 参数支持 `haiku` / `sonnet` / `opus` / `fable`；下表的"轻/中/强"按此映射。

| 工作 | 档位 | 说明 |
|---|---|---|
| 需求讨论、阶段划分、架构设计、取舍 | **强**（Opus/Sonnet/主模型） | 影响全局，错误代价最高 |
| 教学型 brainstorming（差距/概念/代码落点/反问） | **强** | 教学质量决定心智模型，不能下放 |
| 讲解卡、教学文档、心智模型、Q&A 回答 | **强** | 教学质量是项目目标之一，不能外包给轻模型 |
| 高风险实现：Agent Loop、工具执行、Compaction、Session、Unity 线程 | **强或中**（Sonnet/Opus） | 语义微妙，错误难查 |
| 代码搬运/翻译/生成（类型、DTO、协议适配、测试脚手架、重复实现） | **轻**（Haiku） | 方向已定，机械性高；失败升级 |
| 普通实现：简单工具、纯函数 | **轻起，失败升级**（Haiku → Sonnet） | 机械性高，规则明确 |
| 测试脚手架、fixture、mock、重复用例 | **轻**（Haiku） | 模板化 |
| 边界/失败模式测试设计 | **中**（Sonnet） | 需要判断哪些边界值得测 |
| 高风险管理代码审查 | **强**（Opus/Sonnet） | 跨文件推理、语义对照 |
| 机械一致性审查：格式、映射表、状态列 | **轻**（Haiku） | 规则明确 |
| 上游源码扫描、定位、grep、文档摘要 | **轻**（Haiku / Explore） | 广度大、判断少 |
| 多份资料综合、写结论 | **强** | 需要归纳与取舍 |
| 提交信息、状态更新、文档格式化 | **轻**（Haiku） | 机械 |
| 调试 | **强主导 + 轻执行** | 强模型定位，Haiku 跑命令/收日志 |

## 五、成本纪律

1. **强模型想，轻模型打。** 强模型写讲解卡/测试计划/关键接口；Haiku 做批量实现与格式化。
2. **先定契约再分派。** 接口、事件名、类型由强模型定；Haiku 不在设计上做决定。
3. **审查只看 diff + 测试输出。** 不要把整个仓库塞给 reviewer。
4. **批量机械任务合并。** 多个文件同一类改动交给一个 Haiku agent，不要一文件一 agent。
5. **搜索用轻模型。** 广度扫描交给 Explore/Haiku；综合结论回到强模型。
6. **教学不外包。** 教学文档可以 Haiku 排版，但内容必须强模型写/审。
7. **按风险分配，不按单价分配。** 高风险模块用强模型；省下的钱会在调试里加倍花掉。
8. **上下文从简。** 给子 agent 的 brief 只含必要文件和结论，不复述整份文档。
9. **缓存友好。** 固定提示词结构，避免每次重读大文件。
10. **失败升级，不原地重试。** 见下节。

---

## 六、升级阶梯

```
Haiku 失败 2 次 → Sonnet
Sonnet 失败 2 次 → Opus/主模型
Opus 仍失败 → 停下来讨论设计，不继续堆重试
```

- "失败"指：测试不过、行为与 pi 对照不一致、review 发现实质问题。
- 升级时把"失败证据"（测试输出、diff、对照结果）交给上一档，不重新描述需求。
- 同一档不无限重试；超过 2 次说明问题在理解或设计，不在模型档位。

## 八、反模式

1. 让 Haiku 做架构设计或接口取舍。
2. 让强模型批量改几十个机械文件。
3. 同一档失败后原地重试，不升级、不回头查理解。
4. 把整个仓库/全部文档塞给 reviewer 或子 agent。
5. 让 Haiku 写教学结论，强模型只做排版。
6. 单个移植文件也走全套 SDD。
7. 为省 token 砍掉对照验证或教学文档。
8. 高风险模块用轻模型硬扛，最后靠人肉调试补。
9. 把"范围裁剪"当进度：以"用不到"为由删除公共类型/接口/字段，制造下游返工。
