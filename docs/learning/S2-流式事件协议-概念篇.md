# S2 概念篇 · 流式事件协议

> **阶段**：S2（pi-ai 流式事件协议）。
> **原则**：先建立"生成过程如何流动"的宏观理解；字段细节留给契约篇与源码。
> **上游**：pi `packages/ai/src/types.ts:811-840`、`utils/event-stream.ts`、`packages/agent/src/agent-loop.ts:417-460`；pi.net `src/Pi.Ai/Stream/AssistantMessageEventStream.cs`、`Types/AssistantMessageEvent.cs`。
> **我们的实现**：`src/PiUnityAgent.Ai/Events/`。
> **配套**：`S2-流式事件协议-契约篇.md`、`Q&A.md` Q12–Q17。

---

## 1. 它解决什么问题

S1 定义"最终消息长什么样"；S2 定义"这条消息在生成过程中如何流出来"。

没有 S2，调用方只能 `await` 一个最终消息：

- UI 无法逐字显示，只能等整段返回；
- 用户无法中途取消并保留已生成内容；
- 各家 provider 的流式格式差异会渗透到 agent loop；
- 模型/网络失败只能以异常穿透，无法成为数据。

S2 把"一次模型回复的生成过程"抽象成**统一的事件协议 + 单消费者流容器**：

> **S1 定终点，S2 定旅程。**

---

## 2. 在系统中的位置

```
S3/S4/S5 provider adapter（含 Faux）
        │  Push 事件
        ▼
AssistantMessageEventStream（S2）
        │  单消费者异步迭代
        ▼
S7 agent loop / UI
        │
        ▼
AssistantMessage（S1）→ S10 落库
```

S2 **不是** SSE 处理器。SSE 只是最常见的传输；S3/S4/S5 负责解析传输、翻译厂商字段；S2 定义的是翻译之后的语义事件。Faux 完全不联网，也能产出同样的 S2 事件，就是证明。

## 3. 从字节到事件：五层管线

```
HTTP 响应字节
   │ ① 传输：TCP/TLS 分块到达，UTF-8 字符可能跨 chunk
   ▼
SSE 帧（data:/event:/空行；OpenAI 还有 [DONE] 哨兵）
   │ ② SSE 解析：跨 chunk 拼行、按空行切事件
   ▼
厂商 JSON（chat.completion.chunk / content_block_delta / response.output_text.delta…）
   │ ③ provider adapter：取 delta、映射 stop_reason、错误、工具参数
   ▼
S2 事件（text_delta / thinking_delta / toolcall_delta / done / error）
   │ ④ 流容器：缓冲、终态、计时、取消
   ▼
UI 状态机 / agent loop
```

每一层只关心自己那层的形状。**S2 不需要知道 SSE，UI 也不需要知道厂商 JSON。**

## 4. 流式文本存在哪？

### 4.1 字节不进入消息

- HTTP 字节只存在于网络缓冲；
- SSE 解析器负责跨 chunk 拼行、按 UTF-8 解码；
- 进入 `AssistantMessage` 的已经是**解码后的 `string`**，不是字节数组。

### 4.2 按内容块累加

一条 assistant 回复不是一个大字符串，而是块列表：

```
Content = [
    ThinkingContent { Thinking = "先看伤势..." },
    TextContent     { Text = "左臂有旧伤" },
    ToolCall        { Arguments = {...} }
]
```

- `text_delta` → 当前 `TextContent.Text` 追加；
- `thinking_delta` → 当前 `ThinkingContent.Thinking` 追加；
- `toolcall_delta` → 当前参数 JSON 字符串追加，**结束时才解析**。

### 4.3 C# 的 string 是不可变的

`text = text + delta` 不是原地追加字节，而是**每次创建新字符串**。

| 实现 | 做法 | 代价 |
|---|---|---|
| 直接拼 | 每个 delta 新建字符串 | 长文本理论 O(n²) |
| Builder 累加 | 内部 `StringBuilder`，只在发事件/结束时物化 | 实现稍复杂，线性 |

pi 原版是活对象，直接改 `block.text`（JS 引擎内部有 rope 优化）。我们的 Faux 目前直接拼；S4/S5 真实 provider 建议内部用 `StringBuilder`。

> **SSE chunk ≠ token**：一个 chunk 可能含多个 token，一个 token 也可能跨多个 chunk。delta 的边界是传输边界，不是语义边界。

## 5. 前端如何"流"起来

UI 维护一个状态机：

| 事件 | UI 动作 |
|---|---|
| `start` | 创建一条空的 assistant 消息（pending） |
| `text_start` | 在 content 里追加空 `TextContent`，记住 index |
| `text_delta` | 把 delta 追加到对应文本块，重绘 |
| `text_end` | 用 end 的权威文本覆盖该块 |
| `thinking_*` | 同上，渲染到"思考中"区域 |
| `toolcall_delta` | 更新参数预览（不是最终 JSON） |
| `done` | 用 final 替换整条消息，结束"生成中"状态 |
| `error` | 展示错误；保留已生成内容（如果有） |

工程要点：

- **单消费者**：UI 和 agent loop 不能各读一遍；通常 agent loop 是唯一消费者，再把 `message_update` 转发给 UI（pi `agent-loop.ts:417-460`）。
- **Unity 主线程**：provider 在后台线程 push，UI 更新必须 marshal 回主线程（Host 层职责，S13）。
- **节流重绘**：按帧或按时间聚合，不要每个 delta 都触发布局。
- **最终替换**：`done` 的 final 是权威，可能和 UI 拼出来的文本有细微差异。

## 6. 核心概念

### 6.1 事件三族

```
生命周期：start
内容块：  text_start → text_delta* → text_end
          thinking_start → thinking_delta* → thinking_end
          toolcall_start → toolcall_delta* → toolcall_end
终态：    done  或  error
```

### 6.2 delta / partial / final

| 概念 | 是什么 | 例子 |
|---|---|---|
| **delta** | 这次新增的一小段 | `"旧"` |
| **partial** | 从开始到现在的累计消息 | `Text = "左臂有"` |
| **final** | 终态权威消息 | `Text = "左臂有旧伤"` |

每个事件都带 `Partial`。它反复出现，是因为**每个事件都自带一份"到目前为止的完整消息"**：UI 拿单个事件就能渲染完整状态，agent loop 可以直接替换上下文。

**权威性**：`*_end` 和 final 才是最终值。工具参数 delta 是 JSON 碎片；partial 里的参数可能还是 `{}`；脱敏思考可能 `start` 时已完整、没有任何 delta。

### 6.3 contentIndex

`ContentIndex` 是**最终 `Content` 数组中的位置**，不是"第几个块事件"。一条回复可以有多个块并存（思考、文本、多个工具调用），事件必须能归属到正确位置。

### 6.4 单消费者

流不承诺广播。一个消费者按序读完；事件在消费者开始前按 FIFO 缓冲；无背压。

要多方观察（UI + 日志 + telemetry），应在 agent 层转发，而不是开两个迭代器。

### 6.5 partial 的两种实现哲学

| | pi 原版 | pi.net / 我们 |
|---|---|---|
| partial | 共享活对象，随生成增长 | 不可变快照，每个事件一份 |
| 事件里的 partial | 引用 | 快照 |
| 代价 | 别名突变风险 | 每事件分配 |
| 收益 | 零拷贝 | 线程安全、可记录、无隐式突变 |

我们跟随 pi.net，并在契约篇记录偏离与代价。

## 7. 终态：Done、Error、Aborted

### 7.1 Done 的四种 reason

`Done` 是**正常终态事件**，携带最终消息；它不等于"成功"。

| Reason | 含义 | 后续动作 |
|---|---|---|
| `Stop` | 模型自然结束 | 本轮完成 |
| `Length` | 达到输出上限，被截断 | 带工具调用时全部判失败；否则收尾/压缩 |
| `ToolUse` | 模型要求调用工具 | S7 执行工具，回填结果，进入下一轮 |
| `Deferred` | 厂商延后响应（长任务/批处理） | 用 `Deferred` 句柄稍后取回 |

### 7.2 Error 的来源

| 来源 | 例子 |
|---|---|
| HTTP/网络 | 非 2xx、DNS、TLS、连接重置、超时 |
| 传输/协议 | 流结束却没有 finish_reason；SSE/JSON 解析失败 |
| 厂商错误载荷 | SSE 内 error 对象；内容过滤/拒答；invalid request |
| 认证/配置 | key 缺失、无效、baseUrl 错 |
| 限流/过载 | 429/503 |
| 本地适配器 | 未知 provider；Faux 空队列；Factory 抛错；未知内容块 |

注意：

- HTTP 200 也可能带错误（错误藏在 SSE 事件里）；
- `ErrorMessage` 给人看；`RawStopReason` 是厂商原始码，只做诊断；
- Error 终态消息不一定内容为空，很多 provider 会保留已生成部分。

### 7.3 Aborted

`Aborted` 是**被叫停**的终态，不是厂商故障。来源：用户停止、宿主取消、超时、agent/session 中止。

`Error` = "环境坏了"；`Aborted` = "人叫停"。两者必须分开，否则会出现"用户点了停止，系统自动重试"。

## 8. 取消到底取消了谁？

| 取消谁 | 效果 | 不做的后果 |
|---|---|---|
| **消费侧 token**（迭代器 / `WaitForDone`） | 不再读事件 | 生产者可能继续推，unbounded 缓冲继续涨 → 内存泄漏 |
| **生产侧 token**（`StreamFn` / `SimpleStreamOptions`） | provider 停止读/推，发 `Aborted` 终态 | 厂商请求可能继续跑、继续计费 |

**只取消消费侧，不等于停止生成。**

厂商侧如何停：

- **标准 SSE**：没有通用 "stop generating" 消息；实际做法是**客户端中止 HTTP 请求/关闭连接**，厂商检测到断开后停止；
- **显式取消 API**：部分厂商为后台/延后任务提供 cancel 端点（pi 的 `cancelDeferred`）；
- 底座不能保证厂商立刻停止计算，只能保证本地不再消费并尽快中止请求。

## 9. 半截输出的归宿

| 情形 | 半截 assistant 消息 | 下一轮 loop |
|---|---|---|
| `ToolUse` | 保留 | 与工具结果一起进入下一轮 |
| `Length` | 保留 | 工具调用全部判失败，错误结果进入下一轮 |
| `Error` / `Aborted` | 保留在 transcript | **本轮立即结束**；是否回放给模型由上层决定 |

建议：

- 展示：保留，让玩家看到已经生成了什么；
- 回放：半截回答对模型是噪声，通常过滤或替换为说明；
- 工具调用：Aborted/Error 后一律不执行。

## 10. 常见误区

1. **"S2 就是 SSE 处理器"** —— 不是；S2 是语义层，SSE 在 provider adapter 里。
2. **"SSE chunk 就是 token"** —— 不是；边界是传输边界。
3. **"partial 会原地变"** —— pi 原版会，我们的快照不会。
4. **"有 delta 就够了"** —— `*_end` / final 才权威；脱敏思考可能没有 delta。
5. **"事件流可以广播"** —— 单消费者。
6. **"done 就是成功"** —— `Length` 和 `ToolUse` 都不是成功。
7. **"错误应该抛异常"** —— 模型错误是终态事件；异常只表示基础设施坏了。
8. **"事件要落库"** —— 落库的是最终消息；事件是瞬态的。
